================================================================================
1. WHAT THIS SITE IS
================================================================================
Public site for the Auburn University Vietnamese Student Association (VSA).

Architecture:
  - Public pages = static HTML at the web root
  - Hydrated by assets/js/site.js fetching api/content.php (JSON CMS content)
  - PHP for admin CMS, content API, uploads, newsletter, FAQ ask, construction
    mode, SEO helpers (robots.php / sitemap.php), backup
  - No framework, no Composer, no build step, no Node bundler

Do NOT convert public pages to PHP templates / SSI. Keep static HTML + API.

Navy placeholder boxes (rendered in JS) stand in wherever a CMS image has not
yet been uploaded.

================================================================================
2. STACK REQUIREMENTS
================================================================================
Required:
  - Apache (mod_rewrite, mod_headers recommended)
  - AllowOverride so per-directory .htaccess files work (critical for denies)
  - PHP 7.4+ (polyfills for str_contains / str_starts_with / str_ends_with;
    match() removed). Prefer PHP 8.1 or 8.2. Will NOT run on PHP 7.0–7.3.
  - PHP GD extension (image upload resize/recompress in includes/image_optimize.php)
    — optional; uploads still work without resize
  - Writable directories on the server:
      data/     (runtime JSON + hashes; git-ignored contents)
      uploads/  (CMS media; git-ignored contents)

Nice / expected in production:
  - HTTPS (session cookies set Secure when HTTPS is detected)
  - Cloudflare in front (optional). If used: cache /assets/ and /uploads/;
    do NOT aggressively cache /admin/ or /api/.

Subdirectory hosting (e.g. https://university.edu/~vsa/):
  - Supported without a rebuild. Public pages use relative hrefs and assets;
    site.js derives the app base from its own <script src> (override with
    window.VSA_BASE = "/your/path" before site.js if auto-detect is wrong).
  - Session cookie auto-scopes to the mount path (see §7).
  - If clean URLs (e.g. /~vsa/events) 404: edit root .htaccess and uncomment
    `RewriteBase /~vsa/` set to the real mount path.

Dev (local):
  - PHP built-in server: php -S 0.0.0.0:8000 -t .
  - Built-in server does NOT process .htaccess — denies must be verified on Apache
  - Image URLs are root-relative (uploads/x.png); admin previews prefix ../
  - Validate PHP: php -l <file>

7. AUTH / SECURITY (HIGH LEVEL — NO SECRETS)
================================================================================
Multi-user admins: data/users.json via includes/users.php
Legacy/root password resolution order:
  1) env ADMIN_PASSWORD_HASH
  2) data/.admin_password_hash
  3) no fallback — login fails closed if neither a valid users row nor hash exists
No plaintext password or fallback hash ships in source.
Store new credentials offline — never in this file or in git.

Sessions (includes/auth.php):
  HttpOnly, SameSite=Lax, Secure when HTTPS detected
  Cookie path is auto-scoped to the app mount: domain-root installs use "/";
  subdirectory installs (e.g. /~vsa/admin/…) scope the cookie to /~vsa so a
  neighboring app on the same host cannot read the admin session.
  Expires after 2 h idle or 12 h from login (ADMIN_SESSION_IDLE_SECONDS /
  ADMIN_SESSION_MAX_SECONDS env overrides). CSRF is tied to the session — when
  it expires, stolen session cookies and CSRF tokens stop working. Passive
  session.php reads do not extend the idle clock; authenticated saves/uploads do.
  Session cookie is bound to the signing-in browser User-Agent hash (disable with
  VSA_SESSION_BIND_UA=0 if a host proxy rewrites User-Agent).

CSRF:
  Write/admin APIs require X-CSRF-Token (or form csrf field)
  Token from session via csrf_token() / verify_csrf()
  Admin + public write APIs also require same-origin (Origin/Referer host match).

Security headers (includes/security.php + root .htaccess):
  HSTS (HTTPS), X-Content-Type-Options, X-Frame-Options, Referrer-Policy,
  Permissions-Policy, COOP, CORP (JSON APIs), CSP on HTML (fonts + media embeds),
  X-Permitted-Cross-Domain-Policies, no-store on admin/API JSON, X-Robots-Tag
  noindex on admin. TRACE/TRACK blocked. Production HTTPS redirect in .htaccess
  (comment out for local http dev). /.well-known/security.txt (RFC 9116).

Blocked IPs:
  data/blocked_ips.json; admin UI with Site blocks + Unsubscribe cooldowns sections;
  auto-block after repeated failed logins and construction spam thresholds;
  unsub rate-limit rows use source=unsub_cooldown (soft lock — browse OK,
  unsubscribe blocked until expiry or Clear cooldown); posts Messages alert
  (see admin Messages / Blocked IPs copy)

Activity log:
  data/activity_log.json; root-only admin view; secrets stripped from meta
  IP via client_ip() (REMOTE_ADDR; CF-Connecting-IP when peer is CF edge OR
  loopback — so local cloudflared → Apache does not log only ::1)

Error log (includes/errorlog.php):
  Admin APIs run with display_errors off, so fatals would otherwise be silent.
  config.php installs vsa_install_error_handlers() on every request: uncaught
  exceptions + fatal shutdown errors land in data/error_log.json (capped 200,
  repeats within 5 min bump a count) and mirror to the host error log.
  Surfaced root-only on Admin → Dashboard → "Site health" + a needs-attention
  chip. admin/health.php (root, CSRF) reads/clears.

Server uptime (includes/uptime.php):
  Heartbeats written to data/uptime.json (throttled ~5 min) from api/content.php
  and Admin dashboard load. Gaps ≥ 2 h between heartbeats are recorded as
  "quiet gaps" (possible outages) when traffic returns. Shown on Admin →
  Dashboard → "Server uptime". GET api/health.php forces a heartbeat and returns
  JSON for free external monitors (UptimeRobot etc.). Quiet nights with no
  visitors are normal — not proof the host was down.

HTTPS / Secure cookies:
  is_https_request() trusts X-Forwarded-Proto / CF-Visitor when REMOTE_ADDR
  is a Cloudflare edge IP or loopback (not via spoofable headers from the open internet)

Public API rate limits: includes/security.php public_api_rate_check()
CMS URL sanitization: sanitize_cms_urls() blanks unsafe href/image/videoUrl/etc.
  on save and on public content API output

Construction mode: site.constructionMode in CMS; public overlay + optional
admin unlock via construction-auth APIs. Full CMS JSON is withheld from
unauthenticated / non-preview clients (api/content.php gate payload).
site.js does not hydrate page content under the gate for visitors.

Root .htaccess also 403s tools|docs|data|includes|workers (belt-and-
suspenders with nested Require all denied).

12. RECREATE FROM SCRATCH (STEP-BY-STEP)
================================================================================
Any Apache + PHP host: php tools/check-hosting.php → php tools/pack-deploy.php
  [--with-data] [--with-uploads], then upload/extract the zip at the web root.

A. Server
  1. Provision Apache + PHP (+ GD) with AllowOverride for the vhost docroot.
  2. Point docroot at this project root (where index.html lives).
  3. Ensure data/ and uploads/ are writable by the PHP user.
  4. Enable HTTPS (and Cloudflare if used).

B. Files
  1. Upload/deploy the full tree (git clone or zip), INCLUDING denied dirs
     (includes, tools, docs, data/.htaccess, uploads/.htaccess). Prefer
     tools/pack-deploy.php (excludes .git, node_modules/).
  2. Do not rely on the PHP built-in server for production (.htaccess ignored).
  3. Verify deny checklist (§10). Run php tools/check-hosting.php when CLI exists.

C. First boot
  1. Visit / — public HTML should load; site.js fetches /api/content.php
     (defaults if no content.json yet).
  2. Visit /admin/ — sign in with handoff credentials; CHANGE PASSWORDS.
  3. Fill CMS sections; upload logo/media; set Join Now + ticket links.
  4. Test newsletter, FAQ ask, events next-up, gallery lightbox, merch sheet.
  5. Optional: Admin → Backup to download a zip after content is ready.

D. Ongoing
  1. Edit via admin for content; use git/deploy for code/CSS/JS.
  2. After CSS/JS edits: bump-assets --bump; check-maintenance.
  3. After chrome edits: sync the chrome blocks from index.html → all pages.
  4. After any meaningful behavior/structure/ops change: update
     docs/SITE-RECREATE.txt and the short notes in AGENTS.md.

E. Reset content only
  - Delete data/content.json (defaults return). Users/uploads/newsletters
    are separate files — do not delete unless intentional.

F. Backup / restore runbook (Admin → Backup; manual — there is no cron)
  What the zip contains (includes/backup.php):
    data/content.json, newsletters.json, newsletter_drafts.json,
    newsletter_unsub_requests.json, faq_inbox.json, users.json,
    construction_messages.json, blocked_ips.json, scheduled_publish.json,
    activity_log.json, mail/<mailbox>.json, .admin_password_hash,
    uploads/* (png jpg jpeg webp gif mp4 webm mov mp3 m4a ogg wav),
    manifest.json.
  NOT in the zip — recreate by hand after a rebuild:
    data/.mail_inbound_secret (regenerated on first /admin/ load; only matters
    if the Mail Worker is ever actually deployed),
    rate-limit / login-attempt files (harmless to lose),
    anything under includes/ or the code tree itself (deploy that from git).
  Restore (root only, Admin → Backup → Import):
    1. Take a fresh backup of the CURRENT server first — restore is destructive.
    2. Import overwrites every file listed above and DELETES all existing
       uploads before writing the zip's uploads back.
    3. "Also restore admin password" is opt-in; leave it off unless the target
       server should adopt the backup's root password. Ignored when
       ADMIN_PASSWORD_HASH env locks the password.
    4. After import the admin reloads. Re-check: Site mode (construction),
       scheduled publishes, mail secret, then sign-in for each user.
  Cadence: download a zip before any code deploy and after big content pushes.
